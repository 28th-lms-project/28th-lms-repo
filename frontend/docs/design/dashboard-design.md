# 대시보드 설계

- 대상 화면: 대시보드 (`/`, `components/main/Main.jsx`)
- 담당: 대시보드 담당자
- 작성일: 2026-11-19
- 상태: 수강생 · 강사 대시보드 구현 완료. 관리자 · 슈퍼관리자 대시보드는 설계 제안 (7장, 미구현)

이 문서는 대시보드의 설계이자 현재 구현 기준입니다. 무엇을 보여 줄지 정할 때 고민했던 선택지와 그렇게 정한 이유도 함께 남깁니다 (9장).
권한 규칙은 `backend/docs/access-control-guide.md`, 버튼 권한은 `frontend/docs/permission-guide.md`, 화면 부품은 `frontend/docs/ui-style-guide.md`를 함께 보세요.

## 1. 확정된 결정

| 항목               | 결정                                                                                                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 영역을 고르는 기준 | **역할 ID가 아니라 "이 사람이 과정에서 무엇인지(관계) + 권한"** (3장). 역할 ID를 비교하면 관리자가 화면에서 권한을 바꾸거나 새 역할을 만들어도 반영되지 않습니다 (가이드 9장 "하지 말 것") |
| 영역               | 수강생 영역 · 강사 영역 (구현) · 관리 영역 (제안, 7장). 한 사람이 여러 영역에 해당하면 모두 보여 줍니다                                                                                    |
| 카드 · 패널 표시   | **권한이 있을 때만** 보이고, 그 API도 그때만 부릅니다                                                                                                                                      |
| 데이터 불러오기    | 과정 목록이 오면 화면부터 그리고, 카드 · 패널은 **자기 데이터가 오는 대로** 채웁니다. 실패한 API는 그 카드에만 오류를 보여 줍니다                                                          |
| 다루는 과정        | 진행 중 과정만 API를 부릅니다. 시작 전 과정은 카드만("D-N 시작"), 종료된 과정은 접힌 패널에 모읍니다                                                                                       |
| 수업일             | **과정 기간 안에서 시간표가 있는 날** (백엔드 SQL 조각 `courseClassDays` 하나로 출석 체크 · 출석 요약이 함께 씀)                                                                           |
| 출석률             | 대시보드는 **지금까지 출석률** = 출석 인정일 ÷ 진행된 수업일. 과정 › 출석률 탭은 서버 값(전체 기간 기준, 수료 판단용)을 "출석률 (전체 기간)"으로 표시                                      |
| 결석 수            | 서버의 **최종 결석** (`totalAbsentCount` = N 기록 + 출석 안 누른 수업일 + 지각 3회당 1회)                                                                                                  |
| 항목을 누르면      | 그 과정 화면(`/my/course/list/:id?tab=N`)의 해당 탭으로 이동 (4-3)                                                                                                                         |
| 다크 모드          | 라우트에 `darkReady: true`                                                                                                                                                                 |
| UI 부품            | 표준 UI만 (`StatCard` · `Panel` · `Progress` · `Badge` · `StatusBox` · `card-grid` · `layout-3col` · `list-group`)                                                                         |

## 2. 화면 진입 흐름 (`Main.jsx`)

```txt
권한 조회 중 ────────────────────────────── 불러오는 중
권한 조회 실패 ──────────────────────────── "내 권한을 불러오지 못했습니다."
과정 조회 권한(COURSE_READ) 없음 ─────────┐
과정 목록 조회 중 ────────────────────────│── 불러오는 중
과정 목록 조회 실패 ──────────────────────│── "내 과정을 불러오지 못했습니다." [다시 시도]
                                          ▼
수강생 과정도, 강사 과정도 없음 ──────────── "대시보드에 보여 줄 정보가 없습니다."
그 밖 ─── 강사 영역(강사 과정이 있으면) + 수강생 영역(수강생 과정이 있으면)
```

- 과정 목록은 `Main`이 한 번만 불러옵니다 (`useMyCourses`). 영역별 과정 배열은 `useMemo`로 고정해서 넘깁니다. 렌더마다 새 배열을 넘기면 아래 대시보드가 매번 다시 요청합니다.
- 두 영역이 함께 보이면 "담당 과정 (강사)" · "수강 중인 과정" 제목을 붙입니다 (`Main.module.css`).
- 관리 영역(7장)을 만들면 이 흐름의 맨 앞에 들어갑니다.

## 3. 영역을 고르는 기준: 과정 관계 + 권한

`GET /course/view`가 과정마다 **로그인 사용자와의 관계**(`myRelation`)를 줍니다.

| `myRelation` | 뜻                                           | 보이는 영역 |
| ------------ | -------------------------------------------- | ----------- |
| `TUTOR`      | 이 과정의 강사로 등록 (`COURSE_TUTOR`)       | 강사 영역   |
| `STUDENT`    | 이 과정의 수강생으로 등록 (`COURSE_STUDENT`) | 수강생 영역 |
| `null`       | 등록 안 됨 (관리자가 보는 다른 과정 등)      | 없음        |

- 둘 다 해당하면 `TUTOR`입니다.
- 조회 범위(관리자는 전체 과정)와 관계 기준(로그인 사용자)은 따로입니다. 그래서 관리자도 자기가 등록된 과정은 관계가 표시됩니다.
- 백엔드 출석 요약도 같은 방식(역할 이름이 아니라 `COURSE_STUDENT` 등록 여부)으로 "본인 것만 줄지"를 판단합니다.

**새 역할을 만들면**: 그 역할에 `COURSE_READ`를 주고 사람을 과정에 수강생이나 강사로 등록하면, 역할 ID와 상관없이 해당 영역이 보입니다.

### 역할별로 지금 보이는 것

| 역할                        | 지금                                        | 이유                                          |
| --------------------------- | ------------------------------------------- | --------------------------------------------- |
| 수강생                      | 수강생 대시보드                             | 수강생으로 등록된 과정                        |
| 강사                        | 강사 대시보드                               | 강사로 등록된 과정                            |
| 조교 (`ROLE_SUPPORTER`)     | "보여 줄 정보가 없습니다"                   | `COURSE_READ` 등 과정 권한이 거의 없음 (9-16) |
| 조회 전용 (`ROLE_READONLY`) | 과정에 등록되어 있으면 그 영역, 아니면 안내 | 관계 기준                                     |
| 관리자 (`ROLE_ADMIN`)       | "보여 줄 정보가 없습니다"                   | **`COURSE_READ`가 없음** (7장)                |
| 슈퍼관리자                  | 등록된 과정이 있으면 그 영역, 없으면 안내   | 모든 권한을 통과하지만 관계는 등록 기준 (7장) |

### 3-1. 과정 단위 권한 원칙 (2026-11-19)

대시보드는 "과정 관계"로 영역을 고릅니다 (3장). 그런데 **백엔드 API 중에는 권한 코드(역할에서 옴)만 보고 "이 과정에서 이 사람이 무엇인지"를 확인하지 않는 곳**이 있어, 대시보드와 기준이 어긋납니다. 이 절은 그 원칙과 고칠 곳을 정리합니다.

#### 원칙: 권한은 두 겹으로 확인

| 겹           | 묻는 것                                  | 어디서                                            |
| ------------ | ---------------------------------------- | ------------------------------------------------- |
| 1. 권한 코드 | 이 **종류의 기능**을 쓸 수 있는 사람인가 | `@RequireAction`                                  |
| 2. 과정 관계 | **이 과정에서** 그 일을 할 위치인가      | 서비스에서 `COURSE_TUTOR` / `COURSE_STUDENT` 확인 |

- **강사 기능** (과제 관리 · 시험 세트 · 채점 · 학생 추가 · 상담 · 면접 등록): 권한 코드 **+ "이 과정의 강사 또는 관리자"**
- **수강생 기능** (출석 · 시험 응시 · 설문 응답): **로그인 + "이 과정의 수강생"**. 출석 체크(`POST /attendances/{courseId}`)가 이미 이 방식입니다
- 이렇게 하면 역할이 무엇이든, 어떤 경로로 그렇게 됐든, **한 과정 안에서는 그 과정의 관계대로만** 행동합니다

#### 왜 역할을 막는 방식이 아닌가

"강사 역할 계정은 수강생으로 등록되지 않는다"는 화면의 학생 선택 목록(`ROLE_STUDENT`만 표시)으로는 맞지만, 다음 경로로 같은 상황이 생깁니다.

- **등록 뒤 역할 변경**: 회원 관리의 역할 변경 · 역할 삭제 때 사용자 이동은 과정 등록 여부를 보지 않습니다 (예: 수강 중인 학생을 보조 강사로 바꿈)
- **서버 미검사**: 학생 추가 API(`addCourseMember`) · 과정 등록(`addCourse`) · 강사 지정(`addtutor`)은 서버에서 역할을 확인하지 않습니다

역할 검사나 역할 변경 금지로 막으면 증상만 막힙니다. 아래 #3(다른 과정 강사의 시험 접근)은 이 경우가 아니어도 생기고, 역할 ID 비교는 가이드 9장에 어긋나며 새 역할(예: 연수생)을 학생으로 넣지 못하게 됩니다.

#### 고칠 곳 (2026-11-19 기준 코드)

| #   | 기능                                                                        | 지금                                                                    | 고친 뒤                                                                                    |
| --- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 1   | ⚠️ 시험 세트 등록 · 공개 전환 · 삭제 · 채점 · 답안 조회 (`ExamServiceImpl`) | **과정 확인 없음** → 모든 강사가 모든 과정의 시험을 다룸                | 이 과정의 강사 또는 관리자                                                                 |
| 2   | ⚠️ 시험 응시 (`createTestAnswerByTestSetId`)                                | 공개 여부만 확인 → **아무 과정의 시험에 답안 제출 가능**                | 로그인 + 이 과정의 수강생                                                                  |
| 3   | 과제 등록 · 수정 · 삭제 (`CourseServiceImpl`)                               | 과정 구성원(**수강생 포함**)이면 통과                                   | 이 과정의 강사 또는 관리자                                                                 |
| 4   | 학생 추가 (`addCourseMember`)                                               | 학생 추가 권한만 있으면 어느 과정에든                                   | 이 과정의 강사 또는 관리자                                                                 |
| 5   | 같은 과정에 강사 · 수강생 동시 등록                                         | 검사 없음 → 강사 대시보드 출석 요약에 본인만 나오고 오늘 출석 집계 403  | 학생 추가 · 강사 지정 때 같은 과정의 반대쪽에 이미 있으면 거부 (역할이 아니라 관계로 판단) |
| 6   | 설문 응답                                                                   | 수강생 확인은 함. 권한 코드(`COURSE_SURVEY_ANSWER`)가 역할에 없으면 403 | 로그인 + 이 과정의 수강생 (권한 코드 불필요)                                               |
| 7   | 면접 · 상담                                                                 | 2026-11-18에 각 서비스에 "이 과정의 강사 또는 관리자" 확인 추가         | 공용 확인 로직으로 교체                                                                    |

**적용 현황 (2026-11-19, `fix/course-access`)**: #1 · #2 · #3 · #4 · #5 · #7 적용. 공용 확인 로직은 `course/service/CourseAccessChecker` (관리자 판단도 이 클래스 한 곳으로 모음). 남은 것은 #6(설문 응답의 권한 코드 제거, 팀 결정)과 관리자 판단의 권한 코드 전환.

이미 원칙대로인 것: 출석 체크 · 오늘 내 출결 · 출석 요약(수강생은 본인만) · 과정 성적 전체 조회(`ScoreServiceImpl`) · 과정의 오늘 출석 현황(수강생 403).

#### 구현 방법

- **공용 확인 로직 하나**: 예) `CourseAccessChecker`의 `requireTutorOrAdmin(courseId)` · `requireStudent(courseId)` · `relationOf(courseId)`. 과정 · 시험 · 면접 · 상담 서비스가 모두 이것을 씁니다
- **관리자 판단도 여기서 한 번만**: 지금 서비스마다 있는 `COURSE_ADMIN_ROLES`(역할 ID 목록)를 권한 코드 기반으로 바꿉니다 (7-5)
- **하지 않는 것**: 역할 변경 금지 · 서버의 `ROLE_STUDENT` 검사. 원칙이 적용되면 수강생이 강사 역할로 바뀌어도 해가 없습니다. 필요하면 회원 관리에서 "수강 중인 과정이 있습니다" 안내만 띄웁니다
- **적용 순서**: #1 → #2 → #3 · #4 → #7 → #5 → #6 (위험한 것부터)
- **테스트**: 기능마다 "이 과정 강사 · 다른 과정 강사 · 이 과정 수강생 · 관리자" 네 경우 (면접 · 상담 테스트와 같은 틀)

## 4. 수강생 대시보드 (구현)

### 4-1. 화면 구성 (위에서 아래로)

| 순서 | 영역             | 내용                                                                                                                                                                    |
| ---- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 수치 카드 5개    | 수강 중 과정 · **출석률 (지금까지)**(지각 · 결석, 주의 표시) · **평균 점수**(채점 끝난 시험만 100점 환산, 채점 중 수) · **응시할 시험** · **남은 과제**(가장 빠른 마감) |
| 2    | 내 과정          | 진행 중 + 시작 전 과정 카드 (기간 · 강사 · 진행률 · 상태 배지)                                                                                                          |
| 3    | 오늘 출결        | 오늘 수업이 있는 과정마다 상태 배지 또는 [출석] 버튼. 오늘 수업이 없으면 패널을 그리지 않음                                                                             |
| 4    | 오늘 할 일 (3열) | 오늘 시간표(교시 · 시각, 지금 수업 "진행 중") · 응시할 시험 · 남은 과제(D-day, D-2부터 주의 색)                                                                         |
| 5    | 종료된 과정      | 접힌 패널, [펼치기]                                                                                                                                                     |

### 4-2. 데이터 (`useStudentDashboard`)

진행 중 과정마다 아래를 병렬로 부르고, 결과가 오는 대로 채웁니다.

| 키           | API                                                        | 권한                       | 쓰는 곳                        |
| ------------ | ---------------------------------------------------------- | -------------------------- | ------------------------------ |
| `summary`    | `GET /{courseId}/attendance/summary` (수강생은 본인 한 줄) | `COURSE_ATTENDANCE_READ`   | 출석률 카드 · 과정 카드 진행률 |
| `scores`     | `GET /scores/{courseId}/me`                                | 로그인만                   | 평균 점수                      |
| `tests`      | `GET /admin/system/{courseId}/testSet` (`submittedYn`)     | `EXAM_SET_READ`            | 응시할 시험 (공개 + 미응시)    |
| `homeworks`  | `GET /{courseId}/homeworklist` (`submittedYn`)             | `COURSE_HOMEWORK_READ`     | 남은 과제 (마감 전 + 미제출)   |
| `lessons`    | `GET /timetable/{courseId}/{date}` (`timeSlots` 포함)      | `COURSE_SCHEDULE_READ_ONE` | 오늘 시간표                    |
| `attendance` | `GET /attendances/{courseId}/today`                        | 로그인만 (수강생 본인)     | 오늘 출결                      |

- 시간표 API는 그날 시간표가 없으면 400을 줍니다. 오류가 아니라 "오늘은 수업이 없습니다"로 봅니다.
- 출석 버튼은 `POST /attendances/{courseId}`입니다. 지각 · 결석으로 기록될 시각이면 누르기 전에 확인 창을 띄웁니다. 시각 안내는 브라우저 시계로, 실제 판정은 서버 시각으로 합니다.

### 4-3. 과정 화면 탭 번호 (`CourseItem`의 `TABS` 순서)

| 시간표   | 2    | 오늘 시간표              |
| 과제     | 3    | 남은 과제 · 마감 전 과제 |
| 시험     | 4    | 응시할 시험 · 채점 대기  |
| 면접일정 | 5    | 다가오는 면접            |
| 설문     | 7    | 설문 응답                |

탭 순서가 바뀌면 `dashboardShared.js`의 `COURSE_TAB`도 같이 바꿔야 합니다.

## 7. 관리자 · 슈퍼관리자 대시보드 (설계 제안, 미구현)

### 7-1. 지금 상태와 문제

- **관리자**는 `COURSE_READ`가 없어 과정 목록 자체를 받지 못합니다. 가진 권한은 회원 · 메뉴 · 역할 관리, 시간표 조회, 과정 성적 조회(`SCORE_READ_COURSE`)입니다.
- **슈퍼관리자**는 모든 권한 검사를 통과해 전체 과정을 받지만, 과정에 등록되지 않았으면 관계가 없어 안내만 봅니다.
- 관리자가 보고 싶은 것은 "내 과정"이 아니라 **전체 현황과 손볼 데이터**입니다. 관계 기준으로는 고를 수 없습니다.
- 수강생 · 강사처럼 과정마다 API를 부르면 과정이 15개만 돼도 수십 번 호출합니다.

### 7-2. 제안: 전용 권한 코드 + 집계 API 하나

| 항목                    | 제안                                                                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 관리 영역이 보이는 조건 | 새 권한 코드 **`DASHBOARD_ADMIN_READ`**를 가진 사람 (관리자에게 부여). 슈퍼관리자는 자동 통과                                                     |
| 왜 전용 코드인가        | 기존 코드 조합(예: `MEMBER_READ_LIST`)으로 정하면 **강사도 회원 조회 권한이 있어서** 관리 영역이 보입니다. 역할 ID 비교는 가이드 9장에 어긋납니다 |
| 데이터                  | `GET /dashboard/admin` 하나 (`@RequireAction(domain = "DASHBOARD", action = "ADMIN_READ")`). SQL에서 집계해 한 번에 줌                            |
| 위치                    | 대시보드 맨 위. 관리자가 과정에도 등록되어 있으면 아래에 강사 · 수강생 영역이 이어짐                                                              |

### 7-3. 관리 영역 화면 구성 (제안)

| 영역              | 항목                   | 내용                                                                                                        |
| ----------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------- |
| 수치 카드         | 과정 현황              | 진행 중 · 시작 전 · 종료 과정 수                                                                            |
|                   | 수강생 · 강사          | 진행 중 과정의 수강생 수 · 강사 수                                                                          |
|                   | 평균 출석률 (지금까지) | 진행 중 과정 전체                                                                                           |
|                   | 출석 주의 학생         | 전체 과정 합계                                                                                              |
|                   | 채점 대기              | 전체 과정 미채점 답안 합계                                                                                  |
| 패널: 과정별 현황 | 진행 중 과정 표        | 과정명 · 강사 · 진행률 · 평균 출석률 · 주의 학생 수 · 채점 대기. 누르면 과정 화면                           |
| 패널: 데이터 점검 | 손볼 데이터            | **시간표 미등록** 진행 과정 (수업일 0) · **강사 미배정** 과정 · 강사 ID가 잘못된 과정 · 과정 기간 밖 시간표 |
| 패널: 회원        | 회원 현황              | 역할별 회원 수 · **로그인이 잠긴 계정** · 최근 가입                                                         |

"데이터 점검"은 이번 대시보드 작업 중 실제로 발견한 문제들입니다 (강사 없는 `000004`, 강사 ID 칸에 과정 ID가 들어간 `000015`, 기간 밖 시간표). 관리자가 화면에서 바로 알 수 있게 하는 것이 목적입니다.

### 7-4. 슈퍼관리자 추가 패널 (제안): 시스템 점검

슈퍼관리자에게만 (`@RequireSuperAdmin` API) 보이는 패널입니다.

| 항목                           | 내용                                                                                                    | 배경                                                                                                                    |
| ------------------------------ | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| DB에 등록되지 않은 권한 코드   | 코드의 `@RequireAction`에는 있지만 `ACTION` 테이블에 없는 코드. 슈퍼관리자 말고는 아무도 그 API를 못 씀 | 이번에 `COURSE_SCHEDULE_READ_*` · `COURSE_INTERVIEW_READ` · `COURSE_DELETE` · `COURSE_SURVEY_STAT_READ`를 손으로 찾았음 |
| 쓰이지 않는 권한 코드          | `ACTION`에는 있지만 코드에 없는 코드                                                                    | 서버 시작 로그(`UnusedActionCodeReporter`)에만 나오던 것                                                                |
| 권한이 아무 역할에도 없는 코드 | 등록은 됐지만 어떤 역할에도 허용되지 않음                                                               |                                                                                                                         |

### 7-5. 만들 때 함께 할 것

- 과정 · 면접 · 상담 서비스의 관리자 판단(`COURSE_ADMIN_ROLES` 역할 ID 목록)을 권한 코드 기반으로 바꾸는 작업과 같이 정하면 좋습니다. 같은 "관리자"를 두 방식으로 판단하지 않게 하기 위해서입니다.
- `DASHBOARD_ADMIN_READ`를 권한 관리 화면에서 등록하고 관리자에게 허용합니다.

| #    | 주제                                            | 선택지                                                                                                                        | 결정 · 이유                                                                                                                                                                                                                                                                       |
| ---- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 9-1  | 대시보드를 고르는 기준                          | ① 역할 ID(`ROLE_STUDENT` 등) ② 과정 관계 + 권한                                                                               | **②** (2026-11-18). ①은 새 역할 · 권한 변경이 반영되지 않고 가이드 9장에 어긋남. 처음에는 ①로 만들었다가 바꿈                                                                                                                                                                     |
| 9-2  | 처음 만들 대상                                  | 수강생 · 강사 · 관리자 동시 / 수강생 먼저                                                                                     | **수강생 → 강사 → 관리자 순.** 샘플 예시가 수강생 기준이었고, 권한도 수강생이 가장 단순                                                                                                                                                                                           |

| 9-4  | 화면 순서                                       | 과정 카드 먼저 / 오늘 할 일 먼저                                                                                              | 한때 "오늘 할 일"을 위로 올렸다가, **과정 카드를 수치 바로 아래로** 되돌림 (2026-11-18). 과정 카드가 아래 오늘 할 일의 맥락이 되고, 학생은 과정이 1~2개라 오늘 할 일이 많이 밀리지 않음                                                                                           |
| 9-5  | 종료된 과정                                     | 진행 중과 같이 나열 / 탭 / 접힌 패널                                                                                          | **접힌 패널.** 같이 나열하면 눈에 걸리고, 탭은 진행 중을 볼 때도 탭 줄이 생김. 종료 과정은 API도 부르지 않음                                                                                                                                                                      |

| 9-7  | 출석률 기준                                     | 서버 값(전체 수업일) / 지금까지(진행된 수업일) / 둘 다                                                                        | **대시보드는 지금까지, 과정 출석률 탭은 전체 기간(라벨 표시).** 서버 값은 과정 중간에 빠진 날이 없어도 낮게 나와(절반 지점에 약 50%) 주의 표시(진행된 수업일 80%)와 어긋남. 두 숫자를 같이 보여 주는 안은 카드가 복잡해져 제외                                                    |

| 9-16 | 조교                                            | 강사와 같은 대시보드 / 미정                                                                                                   | **미정.** 조교는 과정 권한이 거의 없고 과정에 등록할 방법(`COURSE_TUTOR` 같은)도 없음. 역할을 어떻게 쓸지 정한 뒤 결정                                                                                                                                                            |
| 9-17 | 면접 일정 공개 범위                             | 과정 전체 / 수강생은 본인만                                                                                                   | **수강생은 본인만, 강사 · 관리자는 과정 전체, 다른 과정은 403.** 수강생에게 조회 권한을 열면서 반 전체 면접(이름 · 회사 · 일시)이 보이고 다른 과정 ID로도 조회되는 문제를 발견해 고침                                                                                             |
| 9-18 | 상담 접근 범위                                  | 권한만 확인 / 과정 소속까지 확인                                                                                              | **관리자 또는 이 과정의 강사만.** 다른 과정 강사가 연락처 · 역량 진단 · 상담 기록을 볼 수 있던 문제를 고침. 조회 전용 역할도 과정 강사가 아니면 403 (7-5와 함께 다시 정할 수 있음)                                                                                                |
| 9-19 | 관리자 영역 기준                                | 역할 ID / 기존 권한 조합 / 전용 권한 코드                                                                                     | **전용 권한 코드 제안** (7-2). 기존 조합은 강사에게도 열림                                                                                                                                                                                                                        |
| 9-20 | 강사 역할 계정이 다른 과정의 수강생이 되는 경우 | ① 학생 추가 때 역할 검사 · 역할 변경 금지로 막기 ② 팀 규칙(학생 계정을 새로 만듦)으로 운영 ③ 과정 단위 권한(관계 + 권한 코드) | **③** (3-1). ①은 역할 ID 비교라 가이드 9장에 어긋나고 증상만 막음. ②는 등록 뒤 역할 변경 · 서버 미검사 경로를 막지 못함. ③은 다른 과정 강사의 시험 접근 같은 문제까지 함께 해결                                                                                                   |
